# 06 — Session 2026 : gamescope, GNOME 50, overlay, alternatives, enregistrement

Périmètre : statut réel de gamescope en septembre 2026 ; ce qu'une session gamescope (backend DRM, comme `~/NixOs/os/gaming/pegasus.nix`) apporte encore au projet maintenant que la bascule TV en cours de partie n'est plus une exigence ; mécanique d'overlay (OGUI vérifié dans les sources) et son équivalent GNOME ; cage, Plasma Bigscreen, gnome-kiosk ; forme finale de l'enregistrement sans dialogue sous GNOME. Ce fichier prolonge `02-session-capture.md` (patron de session, portail gamescope, scopes systemd) sans le refaire ; là où les deux divergent, c'est parce que CONTEXT-v2 a retiré l'exigence TV.

Versions locales vérifiées (2026-09-10) : gamescope 3.16.23, gpu-screen-recorder 5.13.8, systemd 260.2, MangoHud 0.8.3, OpenGamepadUI 0.45.0 dans le store, `/run/wrappers/bin/gsr-kms-server` présent (`-r-x--x--x root`, produit par `programs.gpu-screen-recorder.enable = true`, `~/NixOs/os/gui/gpu-screen-recorder.nix:2`). Extensions Shell actives : `gameshot@ilyasturki.com`, `hide-cursor@elcste.com`, `whisrs-overlay@eresende.github` (`gnome-extensions list`).

## 1. Statut de gamescope en 2026

**Verdict : pas déprécié. Vivant, central pour le matériel Valve, et cloné par les distributions tierces.** Ce que la rumeur peut désigner, par ordre de vraisemblance : (a) le fork « OGC » qui remplace le gamescope de Valve dans Bazzite/ChimeraOS/Nobara, (b) l'inutilité croissante de gamescope *imbriqué* sur un bureau KDE/GNOME qui fait HDR/VRR nativement, (c) des dépôts de session tiers archivés ou déplacés. Aucune de ces trois choses n'est une dépréciation du projet.

Faits, avec dates :

- **Dépôt.** `gh api repos/ValveSoftware/gamescope` : `archived: false`, `pushed_at: 2026-09-10T20:10:28Z`, 956 issues ouvertes. Tags (dates du commit tagué, API GitHub) : 3.16.28 et 3.16.27 le 2026-08-27, 3.16.26 le 2026-08-26, 3.16.25 le 2026-07-21, 3.16.24 le 2026-05-21, 3.16.20 le 2026-02-06, 3.16.15 le 2025-07-30. Trente derniers commits : Matthew Schwartz (Valve) du 2026-09-02 au 2026-09-10 (« OpenVRBackend: round scaled overlay extents », « wlserver: follow the keyboard layout Steam gives us », « steamcompmgr: keep nested menus visible and correctly stacked », « steamcompmgr: clear PipeWire focus on window teardown », « steamcompmgr: spawn per-connector mangoapps only while… »), Autumn Ashton 2026-09-07 (OpenVR), Olivier Tilloy 2026-09-09 (meson 0.60), Colin Kinloch 2026-09-02 et Eli Bosley 2026-08-26 (WaylandBackend), Sapphire 2026-08-09 (« Process: Drop capabilities when spawning processes »). Le backend Wayland imbriqué, le DRM, l'OpenVR et le HDR sont tous touchés le même mois : rien n'est en fin de vie.
- **Backends.** `src/main.cpp:183-197` liste `auto`, `drm` (« standalone display session »), `sdl`, `openvr`, `headless`, `wayland`, et `--expose-wayland` « support wayland clients using xdg-shell ». Aucune chaîne « deprecated » dans `main.cpp` ; les seules mentions « legacy » sont des variables d'environnement de compatibilité (l. 613, 669). Une nuance vraie : « Steam preloads its overlay into us, but only the SDL backend can draw it » (l. 876-882, `RestartWithoutSteamOverlay`) — l'overlay Steam ne se dessine que dans le backend SDL imbriqué, pas dans le Wayland imbriqué ni le DRM. Et gamescope ne prend toujours pas de clients Wayland sans `--expose-wayland` (fil HN 47454891, ~avril 2026 : « single-tasking gaming focused Wayland compositor that only supports X11 clients ») ; c'est un choix, pas un abandon.
- **Valve l'embarque partout.** SteamOS 3.8 (GamingOnLinux, juin 2026 : Plasma 6.4.3, bureau Wayland par défaut, noyau 6.16, « Initial support for upcoming Steam Machine hardware ») ; la Steam Machine a été livrée le 2026-06-29 (résumés TechRadar/VideoCardz, pages non lues) sur SteamOS, donc sur gamescope-session. À la GDC 2026 (GamingOnLinux, 2026-03-11) Valve détaille la vérification Steam Frame / Steam Machine ; un lecteur y rappelle que l'upscale de gamescope « is stuck at FSR1 ». Steam Frame sous gamescope : non confirmé par une source directe (voir « Non vérifié »).
- **Pilotes.** Phoronix, 2026-09-10 : Mary Guillemard fait exposer la BAR « host cached » dans NVK (pilote Vulkan libre, Mesa 26.3) « needed for gamescope as it explicitly searches for a memory type that is host visible and cached » — donc le pilote libre NVIDIA continue de s'aligner sur gamescope. (L'article Phoronix « NVIDIA Working On Support For Valve's Gamescope » avec la PR de James Jones est l'ancien travail du pilote propriétaire, pas une nouvelle de 2026.)
- **Le fork OGC — source la plus probable de la rumeur.** L'Open Gaming Collective est annoncé le 2026-01-28 (XDA) par Universal Blue/Bazzite avec ChimeraOS, Nobara, ShadowBlip, Playtron, PikaOS, Fyra Labs, ASUS Linux ; le site liste « a downstream fork of Gamescope that expands hardware support » et une politique « upstream first » (KitGuru, opengamingcollective.org). Sur GitHub (`gh api orgs/OpenGamingCollective/repos`) : `gamescope` (fork de `ValveSoftware/gamescope`, branche par défaut `ogc`, poussé 2026-09-08), `gamescope-builds` (« Automated builds for OGC gamescope and sessions »), `gamescope-session` (fork de ChimeraOS, poussé 2026-09-04), `gamescope-session-steam`, `gamescope-session-opengamepadui`, `gamescope-session-ogui-steam`, `steamos-manager` (fork, poussé 2026-09-10), `ScopeBuddy` (« make gamescope easier to use on the desktop », poussé 2026-08-18), `linux`/`kernel-packages` (noyau OGC). La branche `ogc` est rebasée sur les commits Valve (les mêmes commits de Matthew Schwartz y apparaissent datés 2026-09-08), 13 commits derrière `master` le 2026-09-10, dernier merge propre à OGC : PR #19 (écran AYANEO 3 OLED, 2026-09-08). Bazzite 44.20260908 (2026-09-08) embarque « Gamescope 137.7282613d-1 » et « Gamescope Session 0~20260905git.1ddd3a9-1 » avec le noyau 7.2.3-ogc3.1 — un numéro de build qui n'est pas un tag Valve (inférence : c'est le schéma de `gamescope-builds`, non vérifié dans ce dépôt). Lu de loin : « Bazzite n'utilise plus le gamescope de Valve » → « gamescope est déprécié ». En réalité c'est le même code, quelques jours de retard, plus des patches matériels.
- **Dépôts de session déplacés.** `ChimeraOS/gamescope-session` : dernier push 2026-01-06, README inchangé ; sa copie vivante est `OpenGamingCollective/gamescope-session` (2026-09-04). `ShadowBlip/gamescope-session-opengamepadui` : archivé, dernier push 2024-06-06, remplacé par le fork OGC (2026-02-04). Quelqu'un qui tombe sur l'archive lit « deprecated ».
- **Gamescope imbriqué sur bureau : moins utile, pas déprécié.** CachyOS issue #326 (2026-01-29, ouverte) demande de sortir gamescope du méta-paquet gaming : « primarily useful for Gamescope sessions and Steam Deck-like setups », « On KDE Wayland/KWin setups, gamescope remains largely unused ». GNOME 50 (2026-03-18, release.gnome.org/50) : « VRR and fractional scaling … enabled by default », « The mouse cursor now operates independently of the application's frame rate while VRR is active », color-management-v2, partage d'écran HDR ; plus de session X11 (The Register, 2026-03-19). Plasma 6.7.0 (2026-06-16) : HDR, direct scan-out plein écran amélioré. Un guide de mai 2026 (digitnaut) : « KDE Plasma 6 and GNOME 46+ handle a lot of the screen tearing and fullscreen issues that used to require Gamescope », en gardant FSR, HDR, cap FPS et spoof de résolution comme raisons restantes. Le sujet CachyOS « Gamescope-plus removed on packages updates » (forum, 403 à la lecture) va dans le même sens sans que je l'aie lu.

Conclusion plate : le projet est maintenu par Valve (commits de la semaine), livré sur Steam Deck, Steam Machine et SteamOS 3.8, forké et rebasé par toutes les distributions gaming tierces. « Déprécié » ne s'applique qu'à l'idée de *lancer un jeu dans gamescope imbriqué sur un bureau moderne* — et encore, OGC maintient ScopeBuddy exactement pour ça.

## 2. Session gamescope vs GNOME 50

Prémisse changée depuis 02 : plus de bascule TV en séance, sortie unique DP-1. Ce que la session gamescope apporte encore, et ce que GNOME exige à la place. Tout ce qui est marqué « (02) » est détaillé dans `02-session-capture.md`.

**Ce que `resolve-capture-target.js` dépend.** Lecture de `~/NixOs/bin/resolve-capture-target.js` : (1) `focusedRect()` appelle `com.ilyasturki.GameShot` `/com/ilyasturki/GameShot` `GetFocusedWindowRect` (timeout 1000 ms, `try/catch` → `null`) — **c'est le seul usage de GameShot**, et seulement pour le rectangle de la fenêtre focalisée ; (2) `displayState()` appelle `org.gnome.Mutter.DisplayConfig.GetCurrentState` (timeout 2000 ms) — Mutter, pas une extension ; (3) `connectedDrmConnectors()` lit `/sys/class/drm/card*-*/status` ; (4) `toDrmConnector()` : « With a single display connected, that lone connector is the answer regardless of naming ». Sans GameShot, la boucle `MAX_POLLS = 10` × `POLL_INTERVAL_US = 500 ms` tourne 5 s pour rien puis retombe sur `primaryConnector(rects)`. Donc : il ne dépend d'aucune extension pour *fonctionner*, seulement pour viser le moniteur du jeu quand il y en a plusieurs ; avec DP-1 seul branché, ni GameShot ni Mutter ne sont nécessaires, et les 5 s d'attente sont à supprimer avec GameShot.

## 3. Overlay (module futur)

### 3.1 Comment OpenGamepadUI le fait dans gamescope (sources lues)

Fichiers : `core/ui/card_ui_overlay_mode/card_ui_overlay_mode.gd` (334 l.), `core/systems/input/overlay_mode_input_manager.gd` (404 l.), `core/global/launch_manager.gd`, `extensions/core/src/gamescope/x11_client.rs` (1228 l., GDExtension Rust), branche `main` de `ShadowBlip/OpenGamepadUI` (poussé 2026-09-03).

- **Fenêtres.** `_init()` : `overlay_window_id = xwayland_ogui.get_windows_for_pid(PID)[0]` ; `launch_manager.should_manage_overlay = false`. `_find_underlay_window_id()` : parcourt `get_all_windows(root)` et prend la fenêtre qui `has_notification()` (Steam), sinon réessaie chaque seconde.
- **État de base (jeu visible).** `_on_base_state_entered` : `input_plumber.set_intercept_mode(INTERCEPT_MODE_PASS)` ; `set_input_focus(overlay, 0)` et `set_input_focus(underlay, 1)` (atome `STEAM_INPUT_FOCUS`) ; `set_overlay(overlay, 0)` (atome `STEAM_OVERLAY`), et si Steam avait l'overlay, `set_overlay(underlay, 1)`.
- **Menu ouvert.** `_on_base_state_exited` : `INTERCEPT_MODE_ALL` ; `set_input_focus(overlay, 1)`, `set_input_focus(underlay, 0)` ; `set_overlay(overlay, 1)` (et retire celui de Steam).
- **API disponible côté Rust** (`x11_client.rs`) : `set_overlay`, `set_notification` (« UI wants to be shown but not intercept input »), `set_external_overlay` (`GAMESCOPE_EXTERNAL_OVERLAY`), `set_baselayer_window` / `set_baselayer_app(s)` (`GAMESCOPECTRL_BASELAYER_*`), `set_input_focus`, `set_main_app`, `get_focused_window/app`, `set_fps_limit`, `set_blur_mode`, `set_allow_tearing`. Tout passe par des propriétés X sur le XWayland de gamescope — un client xcb Python/Rust fait la même chose en quelques lignes.
- **Côté gamescope.** `steamcompmgr.cpp` : la sélection de `focus.overlayWindow` exige une fenêtre `isOverlay` qui « spans the full root window width or asks for input » (l. 4495-4500) — un Reprise plein écran satisfait la condition ; les `isExternalOverlay` sans `uMangoappMsgType` servent de couche externe (mangoapp) et perdent leur `appID` (« Fixes mangoapp usage when nested », l. 5704-5707).
- **Guide.** InputPlumber, propriété `InterceptMode` sur `org.shadowblip.Input.CompositeDevice` (`/org/shadowblip/InputPlumber/CompositeDeviceN`) : `0 NONE`, `1 PASS` (« except for gamepad Guide events » → passe automatiquement en `2`), `2 ALL`, `3 GAMEPAD_ONLY` (docs `shadowblip.github.io/InputPlumber/usage/`). OGUI pose `set_intercept_activation(["Gamepad:Button:Guide","Gamepad:Button:East"], "Gamepad:Button:QuickAccess2")` (l. 196, 203), reçoit les événements par le signal `input_event` (`_on_dbus_input_event(event, value, dbus_path)`, « ui_guide » → `ogui_guide_ov`, l. 368-379), et **renvoie** au jeu un Guide non consommé par chord (`_send_chord(["Gamepad:Button:Guide"])`, l. 283) avant de repasser en `PASS` (l. 333).

**Séquence Reprise dans la session gamescope** (transposition directe) : au lancement du jeu, Reprise pose `STEAM_OVERLAY=0`, `STEAM_INPUT_FOCUS=0` sur sa fenêtre et `InterceptMode=PASS` ; sur Guide (signal D-Bus) → `InterceptMode=ALL`, `STEAM_OVERLAY=1`, `STEAM_INPUT_FOCUS=1`, Reprise dessine son menu (pause, capture, enregistrement, réglages) par-dessus la dernière image du jeu ; fermeture → l'inverse. Coût : des heures, pas des jours ; tout est du côté compositeur.

**Coût commun aux deux sessions** : `InterceptMode` suppose qu'InputPlumber *possède* la manette pendant toute la session. Aujourd'hui il est « enabled but idle » hors `emu-pad` (CONTEXT) et il pin chaque manette en `ds5-edge`. Le module overlay implique donc « InputPlumber gère toutes les manettes, tout le temps », ce qui change l'identité de la manette vue par chaque jeu (et par Steam Input s'il est jamais utilisé). À décider en amont du module, pas à découvrir.

### 3.2 Sous GNOME

- **Extension Shell (retenu).** Même patron que `whisrs-overlay` : `St.Widget` + `St.BoxLayout` dans `Main.layoutManager`, animations Clutter, données par `Gio.DBus.session.signal_subscribe` ; ajouter `Main.pushModal(actor)` quand le menu est ouvert pour absorber clavier et souris. La manette n'arrive pas à Clutter : c'est le démon qui tient InputPlumber en `ALL` et pousse les actions à l'extension par D-Bus. Les modales du Shell s'affichent déjà au-dessus d'un jeu plein écran, donc le rendu est acquis ; le nom exact de l'API d'unredirect n'a pas été vérifié.
- **Couche Vulkan (rejeté).** MangoHud ne lit les touches que par la connexion `wl_keyboard`/X11 *du jeu* (« maintains its own wl_seat, wl_keyboard, xkb_state », PR #1496 encore à l'état de brouillon), et ça casse dès que le jeu est Wayland natif (issues #1641, #1790, 2025) ; pas de manette, pas de widgets interactifs, un overlay par processus. Rien pour un menu PlayStation.
- **gamescope imbriqué sous GNOME pour avoir les atomes** : rejeté en 02 (`--expose-wayland` casse mangoapp #2334, bugs des backends imbriqués) ; toujours vrai.

### 3.3 Pause d'un jeu

- `systemctl --user freeze <unit>` **existe** (man systemctl 260 local : « Freeze one or more units … using cgroup freezer … supported only on systems that use unified cgroup hierarchy. Unit is automatically thawed just before we execute a job against the unit »). Un scope `game-<slug>-<ts>.scope` (02 §3.4) se gèle donc en une commande, et un `systemctl stop` sur un scope gelé le dégèle d'abord — ce qui neutralise le bug d'« exit qui pend » de l'approche SIGSTOP (SDH-PauseGames #19, 2024-04-27). Noyau (`Documentation/admin-guide/cgroup-v2.rst:1025-1039`) : « Writing "1" … causes freezing of the cgroup and all descendant cgroups … all belonging processes will be stopped and will not run until the cgroup will be explicitly unfrozen … "frozen" value in the cgroup.events control file will be updated » — donc wineserver, pressure-vessel et le jeu gèlent ensemble, et le démon voit `frozen 1` par inotify comme il voit `populated`. `/sys/fs/cgroup/user.slice/cgroup.freeze` est lisible ici (valeur 0).
- **Retours d'expérience Wine/Proton.** Aucune entrée Wine Bugzilla trouvée sur le freezer cgroup (recherches « SIGSTOP wineserver », « cgroup freezer wine »). L'évidence indirecte vient du plugin Decky SDH-PauseGames (SIGSTOP/SIGCONT sur les enfants du reaper, README) : « some games may not like being stopped and resumed too many times over extended periods of play », « some games may stop responding to input once they are resumed » ; issue #32 (2026-05-02) « UE engine games freezing … Sometimes they will resume, but eventually they all freeze » ; #24 « pause not working in rdr2 online » ; #22 « Don't auto pause online games ». Le freezer v2 est invisible aux tâches (contrairement à SIGSTOP, doc noyau v1 « both of these signals are observable from within the tasks being frozen »), mais le saut d'horloge au dégel (GetTickCount/QPC de Wine sur l'horloge monotone) est le même — les gels UE après reprise peuvent donc se reproduire ; non vérifié. Comportement PipeWire d'un client gelé : non vérifié. Recommandation : livrer la pause comme « geler le scope » avec un bouton « tuer », et documenter que les jeux en ligne et Unreal sont à leurs risques.

## 4. Alternatives à gamescope pour une session console

- **cage (wlroots).** 0.3.0 le 2026-04-11 (wlroots 0.20, `wlr-foreign-toplevel-management` « to control windows from an external program », `drm-lease-v1`), 0.3.1 le 2026-06-30, dépôt poussé 2026-09-08. README : « A kiosk runs a single, maximized application », XWayland optionnel à la compilation. Wiki Configuration : « Multiple maximized windows are supported in Cage, but users cannot cycle between them » ; l'application lancée depuis la première « is placed "on top" of the terminal and takes all input until it is closed » — exactement le modèle frontend → jeu → retour, et foreign-toplevel donne au démon un `activate` pour ramener Reprise. Capture : cage est maître DRM comme GNOME, `gsr-kms-server` lit les planes indépendamment du compositeur (02 §2.2) ; non testé. **Correction à la question posée : pas de wlr-layer-shell** — issue #95 « Add support for wlr-layer-shell » ouverte depuis le 2019-12-20, 11 commentaires, absente de 0.3.x ; l'overlay serait donc une fenêtre xdg de plus, empilée par ordre d'ouverture, sans zpos ni focus dédié. Ni HDR, ni FSR, ni mangoapp, ni curseur caché documenté. C'est un gamescope amaigri sans ses fonctions de jeu : il ne bat gamescope sur rien pour ce projet.
- **Plasma Bigscreen.** « Plasma 6.7 is the first release to have Plasma Bigscreen properly included » (GamingOnLinux, mai 2026) ; 6.7.0 sorti le 2026-06-16 ; Phoronix (2026-05-14) : UI fluide, applications plein écran, rien sur la manette ni sur les jeux. C'est un shell plasmashell sur KWin : les jeux tournent sous KWin (HDR, VRR, direct scan-out natifs), la capture passe par le portail KDE (dialogue) ou par KMS, l'overlay par scripts/effets KWin en QML. Techniquement complet, mais c'est un changement d'environnement de bureau pour un utilisateur GNOME et un frontend de plus à ne pas utiliser. Non.
- **gnome-kiosk 50.** Blog GNOME Shell & Mutter (2026-04-01) : compositeur Mutter sans Shell, « automatically starts applications fullscreen », « no panels, dashes, or docks » ; nouveau en 50 : `--no-cursor`, `lock-on-monitor` / `lock-on-monitor-area` / `lock-on-area`, rechargement à chaud de `window-config.ini`, raccourcis VT désactivés par défaut. `CONFIG.md` : règles `match-class`/`match-title` → `set-fullscreen`, `set-above`, `set-on-monitor`, `lock-move`, `set-window-type`. Sessions distantes sous systemd depuis 49 (blog 2025-09-10), d'où l'inférence que `org.gnome.Mutter.DisplayConfig`/`ScreenCast` y sont exportés (fournis par libmutter ; non vérifié pour kiosk). Pas d'extensions, pas de serveur de notifications, pas d'agent BlueZ — les mêmes trous que gamescope — sans HDR-Proton prouvé, sans FSR, sans atomes d'overlay ; `set-above` est le seul empilement contrôlable. Bon « GNOME sans dialogues », mauvaise session de jeu. Non.
- **COSMIC** : non recherché.

Verdict : aucune ne bat gamescope *comme session dédiée*. La vraie alternative à gamescope n'est pas un autre kiosque, c'est GNOME 50 lui-même, qui couvre désormais VRR, HDR, curseur, capture KMS et focus sans aide.

## 5. Enregistrement sous GNOME — forme finale

Vérifié dans `~/NixOs/home/gaming/game-recording.nix` (562 l.) : `-w portal -restore-portal-session no` d'abord (l. 389-436), puis `resolve-capture-target.js` → `-w "$TARGET"` (l. 458-480) ; flags `-f 60 -fm vfr -c mkv -k av1_10bit -ac opus -a default_output -a default_input -s 3840x2160 -ffmpeg-video-opts …` ; `gsr-kms-server` par `programs.gpu-screen-recorder.enable` (`os/gui/gpu-screen-recorder.nix:2`), wrapper présent.

```
gpu-screen-recorder -w DP-1 -cursor "$CURSOR" \
  -f 60 -fm vfr -c mkv -k av1_10bit -ac opus -a default_output -a default_input \
  -ffmpeg-video-opts 'rc_mode=QVBR;global_quality=95;b=16000000;maxrate=32000000;bufsize=64000000' \
  -o "$OUT"
```

- **Encodage** : les valeurs de `-ffmpeg-video-opts` ci-dessus reprennent la commande proposée en 02, pas une relecture de `game-recording.nix` (seule la présence du flag y a été vérifiée) ; à recopier depuis le fichier au moment du port.
- **Cible** : le connecteur DRM. Un seul branché → lu dans `/sys/class/drm/card*-*/status` (`connectedDrmConnectors()` de l'actuel résolveur, sans gjs : trois lignes de Python/Rust). Plusieurs → `org.gnome.Mutter.DisplayConfig.GetCurrentState`, moniteur primaire, normalisation `HDMI-1` → `HDMI-A-1` (commentaire du résolveur). Plus de `-s`, plus d'attente de fenêtre, plus de sélecteur, plus de jeton de restauration.
- **Curseur** : man 5.13.8 « `-cursor yes|no` Record cursor (default: yes) » ; c'est le réglage par jeu de CONTEXT-v2. Effet sur le chemin KMS (plane curseur ignoré) : d'après le man seulement, non testé.
- **Audio** : `-a default_output -a default_input` comme aujourd'hui (« Can be specified multiple times »).
- **Le jeu change de moniteur** : l'enregistrement reste sur `DP-1` — accepté par CONTEXT-v2. Si un jour ça compte, c'est le signal `MonitorsChanged` + segments `mkvmerge` de 02 §3.2.
- **`-w focused`** : man « Record the currently focused window (X11 only) (use with -s option) ». README gsr l. 320 le présente comme repli X11 quand root est désactivé. Sous XWayland-dans-gamescope : non testé, pas retenu (le portail gamescope fait mieux, 02).
- **Capture d'écran** : `gpu-screen-recorder -w DP-1 -o "$JOURNAL/<gameKey>/attachments/<ts>.png"`.

Disparaissent : le sélecteur de portail et ses 60 s, `await-game-window.js`, `resolve-capture-target.js` (ou réduit à `connectedDrmConnectors`), l'extension GameShot, `-s 3840x2160`, `GI_TYPELIB_PATH`.

## 6. Verdict

**MVP : GNOME 50 natif, sans gamescope.** 02 recommandait « gamescope d'abord » *parce que* la bascule TV en séance exigeait un compositeur qui suive le hotplug et un flux de capture qui suive le jeu ; CONTEXT-v2 a retiré cette exigence, et GNOME 50 fournit le reste : VRR par défaut, curseur découplé, HDR/color-management-v2, capture KMS dialog-free déjà câblée, focus qui revient à Reprise par la règle MRU de Mutter, curseur caché par une extension pilotable en D-Bus, notifications/Bluetooth/volume gratuits. Le démon (scope systemd + `cgroup.events`, gsr KMS, `EnableExtension/DisableExtension`, InputPlumber) est identique dans les deux sessions, donc rien n'est perdu à commencer par GNOME.

**Le mode gamescope se construit comme module opt-in, et il vaut le coup quand l'un de ces quatre points arrive :**
1. **Le module overlay** : atomes `STEAM_OVERLAY`/`STEAM_INPUT_FOCUS`/`GAMESCOPECTRL_BASELAYER_*` = quelques heures ; sous GNOME = extension Shell + D-Bus + modale = jours, avec maintenance à chaque GNOME.
2. **HDR pour les jeux Proton** : chemin prouvé sur SteamOS 3.8 ; sous Mutter 50, Proton-HDR non vérifié.
3. **FSR1 / cap FPS / spoof de résolution** par jeu sans MangoHud.
4. **Démarrage console** (autologin, pas de bureau).

Coût du module : la session existe (`pegasus.nix`) ; il manque `dbus-update-activation-environment`, le lien `graphical-session.target`, `xdg-desktop-portal-gamescope` (02 §3.1-3.2) ≈ 2-3 jours, plus le serveur de notifications et l'agent BlueZ (02 §3.5) ≈ 2,5 jours si on veut l'appairage et les toasts dans cette session.

Ce que je ne ferais pas : cage, gnome-kiosk ou Bigscreen (aucun n'ajoute une fonction que gamescope n'a pas, tous retirent des fonctions que GNOME a) ; gamescope imbriqué sous GNOME (02) ; une couche Vulkan pour l'overlay ; SIGSTOP à la place du freezer ; garder GameShot et les 5 s de polling du résolveur.
