Source de vérité de la session de livraison du MVP (docs/plan-v3.html). Relire après chaque compaction.

## v4 — sans démon (2026-09-11)

Décision utilisateur (interview /clarify) : plus aucun processus Universe en arrière-plan ; l'API publique est la crate Rust (hôte PySide6 via PyO3) ; seuls la partie, son enregistrement et le post-process tournent en unités systemd transitoires ; les installations/scans vivent dans le processus appelant. Constats qui ont pesé : le « démon spawné en side effect » n'existait qu'en dev (pas de fichier de service) ; le jeu survivait déjà à son lanceur (scope systemd), c'est l'*observateur* qui ne survivait pas à sa propre mort (la reprise « par son unité systemd » promise par le plan n'était pas implémentée : gsr aurait enregistré jusqu'au disque plein) ; le poids réel était trois clients IPC à tenir synchrones.

Modèle de processus (docs/api.md « Modèle de processus ») : `universe play` (ou l'hôte, en-process) exécute les hooks pre-launch, écrit `state/current-session.json` (O_EXCL), puis `systemd-run --user --unit=universe-game-<id>-<session> -p ExitType=cgroup -p ExecStopPost="<universe> session-end <id> <session>" …` et rend la main. systemd exécute `session-end` quand le cgroup se vide : ligne `sessions.jsonl`, extension curseur restaurée, post_command, hooks session-end (capture arrête gsr et classe le mkv via `universe recording-file`, synchrone), puis post-process (unité transitoire, journal → `universe journal-add`). Le module capture lance gsr dans sa propre unité `BindsTo=$SESSION_UNIT` (le hook post-launch lui-même ne dure qu'une seconde ; d'abord posé sur le mauvais wrapper, relevé par la relecture). `Core::open()` réconcilie un marqueur sans unité active (horodatages `journalctl`). L'hôte lie le cœur (`crates/universe-py` → module `universe_core`, PyO3 0.29, GIL rendu pendant les appels) ; `CoreClient` remplace le client QtDBus : sessions déduites de `Launch` + sonde de `Current`, changements déduits d'une veille `QFileSystemWatcher` sur `games/`, `games/<id>/{,journal,media}` et `state/` ; les travaux (install, scan, media) tournent sur un fil de l'hôte avec rappel de progression.

Supprimés : `universed`, `dbus.rs`, `client.rs`, `daemon_main.rs`, fichier de service D-Bus, `services.dbus.packages`, option home-manager `service`, `kind = daemon`, `UNIVERSE_BUS/OBJECT` (→ `UNIVERSE_BIN` + `UNIVERSE_*_HOME` passés aux hooks), `Cmd::Daemon`, recettes `daemon`/`restart`, index SQLite sur disque (mémoire seulement : pas de contention entre processus). zbus reste comme client de GNOME Shell (extension curseur).

Preuves : sondes systemd 260 (ExitType=cgroup + ExecStopPost acceptés sur unité transitoire, env `--setenv`/`$EXIT_STATUS`/`DBUS_SESSION_BUS_ADDRESS` présents, BindsTo arrête le compagnon, journal persistant) ; jeu-sonde `sleep 8` en backend native : `play` → ligne de session 8 s, marqueur effacé, aucun processus restant, extension ACTIVE ; marqueur orphelin (unité morte) → `status` le clôt (125 s, exit -1) ; Technomancer réel (session 194652) : unités `universe-game-…` + `universe-capture-…` pendant la partie, `stop` → ligne avec `recording`, mkv 36 Mo classé, unité post-process journal lancée, aucun processus universe ; hôte PySide6 sur `CoreClient` (capture d'écran, 53 jeux) ; `cargo test` 19, pytest modules 76, pytest ui 28 (dont un test de `CoreClient` : lecture, écriture, erreur signalée, veille qui voit une entrée de journal écrite par un autre processus).

Trouvé en route : le champ `json` de la sous-commande `journal-add` entrait en collision avec `--json` global (panique clap) → `entry` ; les unités transitoires des hooks n'héritaient pas de `UNIVERSE_*_HOME` → la CLI rappelée ouvrait le cœur réel de `~` → passés dans l'env des hooks ; conséquence directe de ce passage de `PATH` : gsr 6.1.1 du dev shell (nixpkgs du flake) passait devant celui du système, et `/run/wrappers/bin/gsr-kms-server` (5.13.8, setcap, forcément du système) refusait le protocole → aucun mkv. Le flake ne met plus gsr sur `PATH` ; le module NixOS épingle `programs.gpu-screen-recorder.package` à la version du flake pour que la paire soit la même.

Clôture : `nix build path:.#{universe,universe-ui,universe-core-py}` OK (l'hôte embarque `universe_core` et reçoit `UNIVERSE_BIN` par son wrapper), `nix flake check path:.` « all checks passed », `just test` vert (19 cargo, 28 ui, 76 modules ; les tests posent leurs propres `UNIVERSE_*_HOME`/`UNIVERSE_BIN` pour ignorer ceux du justfile), troisième partie réelle après relecture (session 201638, 48 s : unité gsr `BindsTo=` vérifiée par `systemctl show`, mkv 35 Mo classé, marqueur retiré, aucun processus universe), seconde partie réelle (session 195908, 47 s) : « entry handed to the core via universe journal-add », note Markdown rendue, aucun processus universe après coup. Non commité (règle : `/commit` à la demande).

## Phase 0 — résultats

- **T1 umu-run : OK avec une correction.** `systemd-run --user --scope --unit=universe-game-… --collect env WINEPREFIX=… PROTONPATH=<store proton-ge> GAMEID=umu-default … umu-run <exe>` crée le scope instantanément ; `cgroup.events` reflète la vie du jeu (populated 1→0, unité déchargée aussitôt ; inotify MODIFY ou poll POLLPRI sur le fichier ; s'attendre à DELETE_SELF juste après). **Gotcha : il faut lancer avec cwd = dossier de l'exe** (`--working-directory`), sinon The Technomancer sort proprement en 1–2 s. Vrai process (comm=TheTechnomancer) visible 3–8 s après (bwrap apparaît avant : ne pas `pgrep -f`). Arrêt : `systemctl --user stop <scope>` → SIGTERM suffit, tout mort en ~2 s ; un jeu qui sort tout seul fait disparaître le scope avant un `stop` explicite (traiter « unit not loaded » comme fin normale). PROTONPATH résolu en GE-Proton11-5 ; runtime steamrt4 déjà présent. `systemd-cgls --user-unit`. Rapport : scratchpad/phase0/test-1.md.
- **T4 zbus ↔ QtDBus : OK.** Méthode, propriétés (via `QDBusInterface.property()` et `Properties.Get`), signaux `SessionStarted/SessionEnded` et `PropertiesChanged` ×2 reçus 4/4 côté PySide6 ; ~0,1 ms par appel. **Décision confirmée : payloads en chaînes JSON** — `a{sv}` en retour de méthode via `QDBusInterface.call()`/`QDBusReply` est faux ou fatal sous PySide6 6.11 (marche seulement en propriété ou en slot typé `QVariantMap`). zbus 5 : `default-features = false, features = ["tokio"]` ; signaux = fonctions associées générées (`Session1::session_started(&emitter, …)`), propriété = `iface.current_changed(&emitter)` ; récupérer l'`InterfaceRef` par `conn.object_server().interface::<_, T>(PATH)` depuis une tâche ; ne pas tenir `get_mut()` pendant un await. PySide6 : `bus.connect(service, path, iface, "Signal", receiver, SLOT("on_x(QString,QString,uint)"))` avec `@Slot` typé — signature fausse = signal perdu en silence ; PropertiesChanged via `SLOT("f(QDBusMessage)")`. Squelette : scratchpad/phase0/t4/svc, client copié dans docs/probes/qtdbus-client.py. Rapport : scratchpad/phase0/test-4.md.
- **T2 hôte PySide6 à l'écran : OK avec deux contraintes.** Rendu Wayland réel (Qt5Compat FastBlur, SoundEffect joue, QtQml.Models SortFilterProxyModel filtre+trie) ; QKeyEvent postés depuis Python arrivent dans `Keys.onPressed` avant et après perte de focus ; **focus rendu automatiquement à la fenêtre PySide6 à la sortie d'un mpv plein écran (3/3, règle MRU de Mutter)** ; ~60 fps sur DP-1 (59,996 Hz). Contraintes : (1) le `nix shell` ne pose aucun chemin d'import QML — il faut `engine.addImportPath` calculé (résolveur copié dans docs/probes/qml_import_paths.py ; dans le flake, wrapQtAppsHook posera QML2_IMPORT_PATH) ; (2) `QtQml.Models` : propriété `model` (pas `sourceModel`), pas d'`ExpressionFilter`, et **`FunctionFilter` segfaute** (3 repros) → les filtres à expression (FavouritesPage `favorite || pinned`) passent par un proxy Python (QSortFilterProxyModel sous-classé). Capture d'écran : `gdbus … Shell.Screenshot` refusé (AccessDenied) → `window.grabWindow()`. Rapport : scratchpad/phase0/test-2.md.
- **T5 gogdl : OK, avec un danger découvert.** `goggame-<id>.info`/`.hashdb` sont des fichiers ordinaires du dépôt GOG (`isGogDepot`) : réécrits par tout `download/update/repair` réussi (mtime change, contenu = celui du build servi) → le suivi des mises à jour par comparaison `buildId` local vs `content-system.gog.com/products/<id>/os/windows/builds?generation=2` (branch==null, dernier date_published) tient. **Danger : le cache interne de gogdl (`~/.config/heroic_gogdl/manifests/<id>`, global par id, indépendant de --path) était périmé (build 2023) → `gogdl update` a calculé un faux diff, tronqué des fichiers réels puis bloqué (hang 5 min)** ; l'agent a réparé Mini Metro (`GOGDL_CONFIG_PATH=<neuf> gogdl repair … --path`, 171 fichiers, tailles et .info identiques à la sauvegarde). Règles pour le module gog : (1) `GOGDL_CONFIG_PATH=$XDG_DATA_HOME/universe/modules/gog/gogdl` dédié ; (2) décider soi-même du besoin de mise à jour (buildId) et n'appeler `update` que si nécessaire ; (3) toujours sous timeout, tuer sur `[TASK_EXEC] CRITICAL` ; (4) stdout de download/update n'est pas du JSON (progression sur stderr : `Progress: ([\d.]+) (\d+)/(\d+)`) ; `info`, `import`, `auth` impriment du JSON pur. `download` ajoute le dossier du jeu à --path, `update/repair` non.
